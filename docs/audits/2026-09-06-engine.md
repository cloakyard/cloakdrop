# Download engine audit — 2026-09-06

Scope: ordinary HTTP/HTTPS/FTP/implicit FTPS transfers, segmentation, retry/resume, task cancellation,
mirror handling, request credentials, staging/publication and their test coverage. Media discovery and
dependency currency are covered by the companion audits. No additional dependency was introduced.

## Findings and fixes

| Finding | Impact before this audit | Implemented correction |
| --- | --- | --- |
| Unknown-size whole-body retries sought to byte zero without truncating staging | A shorter successful retry retained the previous attempt's suffix, while the UI reported only the new body's size | Every whole-body attempt truncates staging before writing; ranged resume retains its existing bytes |
| Oversized whole bodies were capped to the probed size | A longer representation could be silently published as a truncated, completed download | Reject excess bytes, including overflow arriving in a separate chunk; invalidate accepted progress so retrying cannot publish the prefix |
| A completed ranged prefix could escape excess-body rejection during mirror failover | Cross-review found that after an oversized trailing chunk, the next mirror iteration could take the already-complete shortcut | Escalate a validation failure immediately when its expected interval was filled, forcing the coherent restart; a two-mirror regression failed before this correction and now passes |
| Whole requests accepted unsolicited HTTP 206 responses | An unknown-size partial body could be published as a complete resource | Require a whole response on the whole-file path; reject unsolicited partial metadata |
| URLSession registry used numeric task identifiers | Replacing sessions after a proxy change reuses those numbers; an old callback could complete, corrupt or cancel the new task's stream | Key handlers by task object identity across sessions |
| Cancellation could arrive between the initial cancellation check and handler registration | A not-yet-started task could finish before registration and strand its response continuation | Resolve the waiter directly on cancellation and recheck cancellation after registration |
| Origin credentials and flattened cookies followed separate Metalink mirrors | Authentication intended for the primary could reach another host, scheme or port | Scope both probes and body requests to the original origin; preserve non-sensitive transfer headers |
| Redirect and challenge authentication lacked explicit origin boundaries | Removing a header alone did not prevent the host-only challenge cache from reusing a HTTPS password on another port/protocol | Strip sensitive headers across redirect origins in both sessions; cache challenge credentials by scheme/host/port and separate proxy credentials |
| FTP body reads had no idle deadline | A server that accepted RETR but stopped sending could occupy its queue slot indefinitely | Apply a per-read deadline; suspend the deadline while consumer backpressure is active |
| FTP parser accepted invalid EPSV ports, negative SIZE values and malformed PASV tuples | Untrusted EPSV values could trap in UInt16 conversion; malformed metadata was accepted | Strictly validate port bounds, delimiters, tuple fields and nonnegative sizes; reject invalid URL ports without trapping |
| FTP multiline replies could consume a partially delivered terminator | A split TCP packet could desynchronize subsequent replies | Require the terminating line's CRLF before consuming a multiline reply |
| FTP command arguments allowed CR/LF or NUL | A path or credential could inject additional protocol commands | Reject framing characters before transmitting any command |
| PASV trusted the address advertised by the peer | NAT configurations could fail; a peer could redirect the data socket to an unrelated address | Use the control host with the validated passive port, consistent with the EPSV path |

## Evidence

The initial new transfer/parser regressions were run against the previous implementation and failed:
14 tests in two suites reported 17 issues. They reproduced the stale suffix, oversized-body publication,
unsolicited partial publication, invalid passive metadata, negative size and incomplete reply framing.
The corrected transfer, parser, existing engine integration and destination suites then passed:
57 tests in five suites.

Further targeted checks passed:

- 24 tests in four suites covering real TCP HTTP transfers, URLSession backpressure, response-head
  cancellation, independent session handler identities, FTP loopback transfers and parser behavior.
- 25 tests in four suites covering whole-body corruption and retry, origin/proxy credential isolation,
  Metalink mirroring, FTP invalid ports, command framing, passive NAT fallback and stalled-body timeout.
- The 64-request cancellation/registration race stress case and the existing stalled-header cancellation
  test both passed after the final cancellation change (two tests, one suite).
- Strict SwiftLint passed on all nine changed engine source files; `git diff --check` passed.

## Existing strengths retained

- Bounded rolling segment scheduling respects the current/manual connection cap on relaunch, including
  persisted work-stealing tails. Actor-owned write reservations prevent overlapping assignments.
- Each ranged response must describe the exact requested interval, compatible size and available
  same-origin ETag; invalid range behavior triggers a coherent whole-file restart.
- Existing tests exercise short reads/retries, range support changes, missing staging files, changed
  remote resources, pause/immediate resume, relaunch against the same database and byte-perfect output.
- Completion verifies configured checksums while bytes remain in staging. Name collision tests verify
  that existing files/directories survive publication races and failed publication remains retryable.
- Ordered manager-to-task persistence handoff and terminal-save draining prevent stale state from
  resurrecting completed/removed downloads. Status events remain separate from lossy progress updates.
- HTTP and FTP body bridges bound buffered chunks and apply producer backpressure.

## Remaining limits and follow-up opportunities

These checks materially improve reliability; they are not proof against every origin, OS failure or
power-loss scenario.

- Equal-length resource changes cannot be detected reliably when an origin supplies no usable validator
  or trusted checksum. Cross-origin mirrors can also serve different equal-length content; a supplied
  whole-file checksum is the strongest existing safeguard. Persisted Last-Modified fallback and stricter
  mirror identity policy are worthwhile future work, with compatibility tradeoffs to resolve.
- A clean EOF from a source that supplies neither length nor checksum cannot reveal that the origin
  intended to send more bytes. Such responses remain intrinsically unverifiable.
- Resume tests cover process/manager replacement and persisted staging offsets, not sudden physical
  power loss. Mid-transfer persistence remains best effort; progress checkpoints do not currently
  establish a transactional durability barrier between file fsync and the database. Disk fault injection,
  surfacing persistence failures, and an explicit checkpoint durability design deserve a separate pass.
- FTP integration tests exercise plain FTP locally. Implicit FTPS still depends on Network.framework
  TLS behavior; explicit AUTH TLS remains unsupported. Full FTP completion replies are drained best effort
  after the expected bytes arrive, and same-size mutation has no FTP validator today.
- Real-network coverage here is loopback HTTP and FTP. It does not substitute for long-duration soak
  testing across real proxies, unreliable Wi-Fi, removable destination volumes and diverse public CDNs.
- Performance architecture remains bounded and parallel; this audit does not claim a measured throughput
  improvement. Transport throughput and memory under sustained multi-gigabyte concurrent load should be
  benchmarked separately from the correctness regressions.
